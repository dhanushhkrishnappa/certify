## 1. Executive Architecture Principle

CERTIFY requires the **simplest, most auditable architecture** that guarantees relational data integrity, strict separation between AI inference and deterministic certification authority, safe isolation of untrusted learner Python code, and truthful cryptographic credential verification.

- **Selected Topology:** **Modular Monolith** (`Node.js + Express + TypeScript` backend, `React + Vite + TypeScript` SPA frontend, `PostgreSQL 16` primary relational store with `SQLite` local/test parity, `Prisma 5.20+` ORM, native `Ed25519` asymmetric signing via Node `crypto`, and isolated subprocess/container worker execution for Python practical tasks).
- **Explicitly Rejected Complexity for V1:** Microservices, service meshes, standalone vector databases (Pinecone/Qdrant/Milvus), WebSockets for text chat, and blockchain/distributed ledgers.

## 3. Deep-Dive Architectural Evaluations (Phase 5 Specific Decisions)

### 3.1 Mastery Model Decision: Constrained BKT + Explicit Evidence Gates
- **Comparison:** We evaluated standard **Bayesian Knowledge Tracing (BKT)** (`pT=0.20, pG=0.10, pS=0.05`) against a **Simpler Per-Concept Evidence Ratio Model**.
- **Findings:**
  1. BKT is already cleanly implemented in `backend/src/modules/mastery/bkt.ts` and tested in `bkt.test.ts`.
  2. The flaw in the repository was **not** the BKT equation—it was feeding BKT from unvalidated chat keywords (`sessions.controller.ts`) and nested-loop multiplication (`assessment.controller.ts`), and treating `meanMastery` as the sole real input to certification (`certificates.controller.ts`).
- **Canonical Decision:**
  - **Retain BKT as the formative/chapter mastery estimator (`ConceptMastery.pMastery`)**, updated **exclusively** from validated assessment observations (Baseline Diagnostic, Formal Chapter Assessments, and Remediation Recovery Checks)—**never** from free-form tutor chat turns.
  - **Never treat BKT probability alone as proof of competence:** Chapter progression requires `pMastery >= 0.70` **and** zero unresolved `NEEDS_REMEDIATION` concepts in that chapter. Course certification additionally requires persisted, passing `CHAPTER` assessments, a persisted `PRACTICAL` sandbox execution attempt (`>= 0.70`), and a persisted multi-turn `VIVA` defense (`>= 0.70`).

### 3.2 Credential Verification & Signing Model Decision
- **Problem:** Prior docs claimed `Ed25519`, while `certificates.controller.ts` used `HMAC-SHA256` with `config.jwtSecret` and never verified the hash on read.
- **Canonical Decision:** Implement **both** Database-Backed Authoritative Status **and** genuine **Ed25519 Asymmetric Digital Signatures (`RFC 8032`)** using Node's built-in `crypto` module:
  1. **Canonical Signed Payload:**
     ```json
     {
       " compositeScore": 0.9125,
       "courseSlug": "python-fundamentals",
       "courseVersion": "1.0.0",
       "credentialId": "CERT-2026-PY-A1B2C3D4E5F6",
       "enrollmentId": "<uuid>",
       "issuedAt": "2026-10-17T00:00:00.000Z",
       "recipientName": "Alex Chen",
       "ruleVersion": "2026.1",
       "tier": "PROFICIENT"
     }
     ```
  2. **Signing:** `crypto.sign(null, Buffer.from(canonicalJson), privateKey)` stored as base64url/hex signature alongside the exact `issuedAt` ISO string in `evidenceSummary`.
  3. **Verification (`GET /api/v1/certificates/:credentialId/verify`):**
     - Reconstructs the canonical JSON payload from the database fields.
     - Calls `crypto.verify(null, Buffer.from(canonicalJson), publicKey, signatureBuffer)`.
     - Checks `certificate.status === "VALID"` and `signatureVerified === true`.
     - If someone modifies `tier` or `compositeScore` directly in the database, `signatureVerified` evaluates to `false` and `isValid` returns `false`!
     - If an administrator revokes the credential (`status = "REVOKED"`), `isValid` returns `false` (`status: "REVOKED"`).
